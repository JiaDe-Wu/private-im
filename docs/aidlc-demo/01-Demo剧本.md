## 0. 主线与原则

**主张**：模型给了所有人平权，顶级模型一句话就能做出六七十分的应用；企业要的是九十分，多出来的那部分在三件事：**能上架、守得住企业自己的规范、人和 AI 都接得住**。这部分模型给不了，要靠企业把规范装进流程。

**讲法：讲"接手前后"，不讲"谁做的"。** 交付物是一个已经能用、界面也不错的 IM。第一幕用企业检查把它过一遍（接手前），第二幕揭晓同一个 App 被 agent 团队按企业规范接手以后的样子（接手后）。台上不主动讲 App 最初是谁做的；被问到时如实回答（见 03"常见追问"）。

**原则**：

1. demo 是一个过程，不是 PPT，不讲故事、不引数据，用短句配画面。
2. **接手前和接手后是同一个 App、同一张检查清单、同一次运行。**
3. **"AIDLC 预制模块"要属实**：每个角色用 AIDLC 官方专家定义（原文副本在规范包 `aidlc/official/`），企业规范放第二层知识目录。
4. 出处如实：开源底座、第三方内容注明来源；被问到时不回避。
5. 不只展示成功的那一次：多次运行的真实数字（包括没成功的）、"并行省时"如实标。

## 2.1 在 demo 里点出 Crew 能力

引擎：**kirocrew-team（「多 Agent 团队」）**，同事开发的 Kiro Crew app（私有仓库，说明见 `orchestrator.md`），v0.1.0；我们的分支 `demo/aidlc-im` 加了"接手已有项目"、四组测试墙、按团队配置选任务模板、线条图标。设计原则第一条是"不造引擎：agent 用 Crew 原生的子 agent，会话、沙箱、审批、审计都用 Crew 的；app 只做编排、看住结果、画出来"（`PLAN.md`）。

| 画面上看到的 | 底下是 Crew 的什么能力 | 依据 |
|---|---|---|
| 侧栏里的「多 Agent 团队」看板 | App 平台：页面和后端由 Crew 加载，后端跑在 Crew 网关进程里 | `app.json`；Crew TENETS"Everything is an app" |
| 每条角色泳道 | Crew 子 agent：每个角色是 Crew 用 kiro-cli 开的会话，在自己的 git worktree 里干活，不带个人记忆 | `backend/team/kc.py`：`include_memory=False, _memory_mode="incognito"` |
| 每个角色开工前的批准 | Crew 的审批 | Crew 审批页 |
| 同时亮起的泳道、排队原因 | Crew 子 agent 管理器：排队、并发上限、内存保护 | README"原理" |
| 工具调用、"做了什么" | Crew 的安全事件日志 | `security_events.jsonl` |
| credits | Crew 用量记账 | `usage/tokens` |
| 打回后接着原来的对话修 | Crew 的会话续接 | `continue_run` |
| 每个角色的模型 | Crew 的模型选择 | `team/team-im.json`（默认 claude-sonnet-5.5；架构师、合规与安全、评审用 claude-opus-5.5） |

**不能说的**：越界写是事后检查（标红但照样合并），不在运行时拦截；角色 agent 不带 Crew 的记忆和经验（故意的），"越用越懂"用 Crew 原生页面演；服务端和安卓在运行里没有编译，以静态检查为准，功能靠部署后人工试用确认。

## 5. 交付物选择

| 候选 | 结论 |
|---|---|
| 唐卡网站 | 不选：不是这支团队做的，CTO 不感兴趣 |
| 游戏 | 不作交付物：用于开场表现"平权"；承载不了企业规范和上架约束 |
| 网页版 IM 从零做 | 不选：复杂度高、一次运行难以做到能用的水平；"从零"也不是企业的真实起点 |
| **Private IM（已经能用的 IM，由 agent 团队接手）** | **选定**：服务端、网页、安卓三端；接手前能用、好看，但安全、合规、上架检查一片红，正好承载三个门槛；"接手已有系统"也是 CTO 每天面对的处境 |
