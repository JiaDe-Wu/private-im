# 第一部分：概览

## 1. 演示目的（Objective）

向企业客户的技术决策者清晰传递一个信息：**模型给了所有人平权，但企业要的是能上架、守得住自己规范、人和 AI 都接得住的软件。Kiro Crew + AWS AI-DLC 把 agent 团队和交付流程预制成模块，企业只需把自己的规范和领域知识编排进去，就能交付这样的软件。**

看完以后，客户应当相信：
- AI 做的软件可以达到企业能上线的标准，而且标准是企业自己定、自己管得住的；
- 这不是一个黑盒产品，而是在开源底盘上用官方模块编排出来的，企业自己也能搭。

并且愿意：拿一个真实需求加上自己的规范，做一次两周的 POC。

## 2. 演示方式（Method）

采用"**三幕剧**"叙事结构，制造从"**人人都能做出的 demo**"到"**企业敢交付的产品**"的强烈对比。

- **开场**：先承认模型很强，用一个公开的游戏合集，让大家被模型惊艳一次。
- **第一幕**：讲者扮演"**挑剔的企业验收人**"。拿一个已经能用、界面也不错的 IM，用企业真正在意的检查去过一遍，揭示"水面以下"的三道门槛。
- **第二幕**：讲者扮演"**AI 团队的指挥者**"。同一个 App 交给一支 agent 团队按企业规范接手：同一张检查清单从一片红变成一片绿；再回放这支团队如何读懂陌生的系统、各司其职、测试说了算、出错能打回。
- **第三幕**：讲者扮演"**平台的搭建者**"。揭开这支团队是怎么搭出来的：用两页证明"模块化、可组合"的条件已经具备——Kiro Crew 的「发现」页（平台上的应用可装可换）和 AI-DLC 的专家与知识目录（专家可选、企业知识可装）；企业只写一页团队配置和自己的规范。
- **结尾**：回到检查清单，留一个问题给客户。

**wow 的设计**：开场的 wow 属于模型，我们主动让给它；第一幕和第二幕是**同一个 App、同一张检查清单**，接手前一片红、接手后一片绿，第一个属于我们的 wow 不靠解释；第三幕揭开"整支团队就是一页配置加一份规范包"，第二个 wow 落到客户自己身上：这个我们也能搭。

## 3. 主要流程（Flow）

| 段 | 时长 | 内容 | 要让人记住的一句话 |
|---|---|---|---|
| 开场：平权 | 1 分钟 | 公开游戏合集，模型一句话做出的游戏 | 一句话做出 demo，已经是最低配置 |
| 第一幕：水面以下 | 1.5 分钟 | 一个已经能用的 IM 去过企业检查，一片红 | 能用不等于能交付 |
| 第二幕：揭晓与团队 | 3 分钟 | 同一个 App 接手后一片绿；手机上看补上的细节；回放 agent 团队的接手过程 | 各司其职、测试说了算、有失败机制 |
| 第三幕：怎么搭出来的 | 3.5 分钟 | 预制模块；Kiro Crew「发现」页；AI-DLC 专家与知识目录；一页团队配置；企业规范包；为什么这样设计 | 底盘和专家可以外购，规范是企业的大脑 |
| 结尾 | 1 分钟 | 回到检查清单，提出 POC | 你敢不敢验收它 |

# 第二部分：现场演示脚本

## 开场：平权（1 分钟）

（讲述）"各位好。今天想和大家聊一个问题：AI 写代码已经这么强了，企业还缺什么？先给大家看个东西。"

（操作）打开游戏合集页面。

（讲述）"这是网上一个公开的合集，一百多个游戏，大部分是开发者用顶级模型，一句话、一次提示做出来的。"

（操作）点开第一个游戏，玩几秒；再点开第二个。

（讲述）"你看这个，三维的，手感很好；这个也是一次生成的。说实话，第一次看到的时候我也很震撼，模型确实已经很强了。

但大家注意一个细节：这些游戏都不用登录，放在 GitHub 上，大家玩个三分钟，觉得好玩，然后一闪而过。

所以在今天，一个精彩的演示，可能只证明了一件事：你用了最新的模型。一句话做出一个能跑的东西，已经成了最低配置。"

## 第一幕：水面以下（1.5 分钟）

**讲者身份：挑剔的企业验收人**

（讲述）"那我们换个场景：如果不是做游戏，而是一个要交到真实用户手里的企业 App 呢？现在，我来扮演一个挑剔的企业验收人。"

（操作）打开接手前的 IM，点几下：聊天列表、群聊、朋友圈。

（讲述）"这是一个已经能用的 IM：好友、单聊、群聊、朋友圈都有，界面也不错。很多企业手上的系统，就是这个状态：能跑，能用，也有人在用。

但作为验收人，我关心的不是它能不能用，而是它能不能交付。"

（操作）切到检查清单对比页，只显示左列"接手前"。

（讲述）"我们拿它过一遍企业真正在意的检查：上架就绪，{18} 条里过了 {y} 条；安全检查发现 {N} 个问题，比如日志里能看到用户的手机号和验证码；App 里找不到注销账号的入口；企业自己的规范，大部分没对上。

这清晰地说明了一件事：企业要的，是水面以下的东西。

第一，能不能上架，应用商店有一整套硬规则；
第二，守不守得住你们自己的规范，安全基线、数据规则，每家企业都不一样；
第三，人和 AI 接不接得住。能跑，但没人说得清它为什么能跑的代码，谁都不敢碰。

许个愿让 AI 再改一遍？出来什么算什么，每敲一次回车，就是开一次盲盒。这三件事，模型给不了。"

## 第二幕：揭晓与团队（3 分钟）

**讲者身份：AI 团队的指挥者**

（讲述）"我们换一种方式：不是许愿，而是把这个 App 交给一支按企业规范工作的 agent 团队，让它接手。"

（操作）检查清单对比页亮出右列"接手后"。

（讲述）"还是这张清单：上架就绪 {x}/18，安全检查 {0} 个问题，企业规范全部通过。"

（操作）举起手机：把系统字体调到最大回到 App；进入设置 → 注销账号页面；在聊天或朋友圈里打开举报。

（讲述）"我们拿手机看一下。系统字体调到最大，布局跟着变、不乱；设置里能注销账号，这是应用商店的硬要求；聊天和朋友圈里都能举报。

这些都是团队接手时补上的，需求里一句都没写。那它是怎么做到的？"

（操作）切到「多 Agent 团队」看板（投影模式），回放时间轴。

（讲述）"这就是接手这个 App 的那支团队。

首先，AI 架构师把这个陌生的系统读懂，反推出它的结构和接口；AI 产品经理把企业的要求拆成一条条可以验收的标准；AI 合规与安全专家把规范包里的应用商店条款和安全基线写成检查，一开始，这些格子全是红的；AI 测试工程师补上护栏：已有的功能一样都不许改坏；然后后端、前端、移动端、运维分头动手；最后，AI 评审只读不改，逐条核对。这些角色，都是 AWS AI-DLC 官方定义的领域专家。

有依赖的按顺序来，没依赖的同时开工。每个角色在 Kiro Crew 里都是一个独立的会话、一个独立的工作目录：写代码的，看不到检查的在想什么。"

（操作）指测试墙。

（讲述）"这面墙是关键。功能、安全、合规、上架四组检查，一开始全是红的。做完了不是 agent 说了算，是测试说了算。"

（操作）跳到一次打回：红格子 → 指向负责的角色 → 修复 → 变绿。

（讲述）"你看这里，这一格没过，系统自动打回给负责的角色。它接着原来的对话改，改完重新跑检查，变绿了。

没有失败机制的 AI 不是自动化，只是把风险藏到了流程后面。"

（操作）打开产出侧栏，依次点开架构师读懂系统后写下的结构说明、合规专家写的上架条款检查。

（讲述）"每一步交付了什么，都能点开看：这是架构师读懂系统以后写下的结构说明，原来没人写过；这是合规专家把应用商店的条款写成的检查。以前文档写给同事看，同事不一定看；现在写给 AI 看，它一个字一个字全看。"

（操作）指"并行省时"和 credits；再切到接手测试的结果。

（讲述）"时间和花费也如实标着：这次墙钟 {a}，一个 agent 从头做到尾估计要 {b}，整次运行 {c} credits。

最后还有一关：我们找了一个完全没参与过的新 agent，只把这些交付物给它，让它加一个功能。它改对了，检查全绿。这才叫接得住。

对于各位的企业来说，这意味着：手上那些能用、但没人敢动的系统，可以交给一支守规矩的团队接着做下去；交付的不是一堆只有原作者看得懂的代码，而是一份换一个人、换一个 AI，都能接着做的工程资产。"

## 第三幕：怎么搭出来的（3.5 分钟）

**讲者身份：平台的搭建者**

（讲述）"那这样一支团队，是不是要花很大力气去搭？其实，大部分是现成的。"

（操作）切到预制模块图。

（讲述）"最底下是 Kiro Crew，一个开源的底盘：会话、并行、审批、审计，它都管了，跑在你们自己的机器上。上面是 AWS AI-DLC 的官方专家：11 个领域专家、2 个只审不做的评审，还有 1 个会按任务难度来组队的编排者。"

（讲述）"凭什么说这是可以自己组合的？给大家看两页。"

（操作）切到 Kiro Crew 的「发现」页，左侧按来源筛选。

（讲述）"第一页，是 Kiro Crew 的「发现」。这里有近百个应用，开发工具、值班运维、自动化，装上就能用，不要了就卸。来源也分得很清楚：Kiro Crew 内置的、团队审核过的内部应用源、未经核实的社区应用源；企业还可以添加自己的应用源，只放自己审核过的应用。我们刚才看的那个团队界面，就是这个平台上的一个应用。也就是说，平台这一层，本身就是模块化的。"

（操作）切到 AI-DLC 官方专家与方法论知识目录，再切到 demo 项目的团队知识目录 `aidlc/knowledge/`。

（讲述）"第二页，是 AI-DLC 的专家和知识目录。14 个官方专家，每个都有自己的定义和方法论知识，这一层由 AWS 维护，升级框架时一起更新。

企业自己的东西放在另一层：团队知识。也是按专家分目录：安全规范放进安全专家的目录，上架合规条款放进合规专家的目录，公司的编码规范放进共享目录。专家一上岗，就自动加载；不用改专家本身，框架升级了，企业的知识也不会丢。规则还可以按组织、团队、项目一级一级往下继承。

专家是可选的，知识是可装的，这就是专家这一层的模块化。"

（操作）切到 `team/team-im.json`。

（讲述）"有了这两层模块，组队就很简单了。整支团队就是这一页配置：每个角色用哪个官方专家、依赖谁、能改哪些目录、最后交付什么。想加一个合规专家，就是在这里加一段。"

（操作）切回测试墙的分组。

（讲述）"刚才放进知识目录的那些规范，在每个项目开工时，会被编译成这面墙上的检查。规范写一次，换一个项目、换一个客户，照样用。

代码 AI 能替你写；但谁能批多少钱、出了错谁担责，那是公司的规矩，不是技术问题。所以，底盘和专家可以外购，规范是企业的大脑，只能自己建。

为什么不让 agent 越多越好？AI-DLC 的设计原则是：每多一条 agent 边界，就多一个信息损失点。所以只在需要独立判断的地方隔离，比如评审；有依赖的，就一份一份验收；没依赖的，才放开并行。

刚才那个团队应用，由我们的工程师 {n} 人、{d} 天搭建完成。"

（操作）依次切到 Kiro Crew 的日程、记忆 / 经验、Tunnel 页面。

（讲述）"它也不只是白天跑：可以排成每天晚上构建、CI 失败自动排查；人纠正过一次的事，会沉淀成经验，下次不再犯；关卡来了，在手机上也能拍板。"

（操作）回到预制模块图。

（讲述）"所以，第一个 9 来自模型，后面的 9，来自组织。"

## 结尾（1 分钟）

（操作）切回检查清单对比页，左红右绿。

（讲述）"所以在这十分钟里，我们看到了三件事：

- 模型已经给了所有人平权，一句话做出 demo，是今天的最低配置；
- 企业的门槛在水面以下：能上架、守得住自己的规范、人和 AI 都接得住；
- 跨过这道门槛，不需要从零造轮子：Kiro Crew 和 AI-DLC 把团队和流程预制好了，企业只需要编排自己的规范和领域知识。

回到今天的主题：每家企业都在用 AI 写代码，分水岭不在用不用 AI，而在于写出来的东西，你敢不敢验收，敢不敢交给整个公司用。

我们的建议是：拿你们一个真实的需求，加上你们自己的规范，一起用两周做一个 POC。到时候，这张清单上的每一条，都是你们自己的标准。谢谢大家。"

## 旁白要点（讲者需要 highlight 的）

1. 开场的 wow 属于模型，要大方承认。
2. 第一幕和第二幕是**同一个 App、同一张清单**：接手前和接手后。不讲这个 App 是谁做的，讲团队怎么把它改到能交付。
3. 角色是 AI-DLC 官方定义的领域专家，团队跑在 Kiro Crew 上。
4. 两页证明"模块化、可组合"：Kiro Crew「发现」页（应用可装可换、来源可管），AI-DLC 专家与知识目录（专家可选、企业知识可装，框架升级不丢）。
5. 做完不是 agent 说了算，是测试说了算；出错能打回、能修复。
6. 交付物接得住：新 agent 只读交付物就能接着改。
7. 整支团队是一页配置；规范包写一次，各项目复用。
8. 数字都来自运行记录，"并行省时"如实标出。

# 第三部分：参考

## 常见追问

| 追问 | 回答要点 |
|---|---|
| 这个 IM 是怎么来的？ | 如实简答："底子是一个开源 IM，我们的工程师在上面加了朋友圈和品牌。企业的系统大多也是这么来的，这正是 AI-DLC 逆向工程阶段要解决的问题。" |
| 为什么不用一个 agent 全做？ | 小任务一个 agent 更快更省。多 agent 的价值在独立检查、权限分开、没依赖的事并行 |
| 代码会不会出企业？ | 运行状态、记忆、审计在自己的机器上；模型推理走 Kiro 服务，按 Kiro Enterprise 数据政策 |
| 能接我们自己的 Bedrock 吗？ | 目前不能，模型只走 Kiro 服务 |
| 一次交付花多少钱、多久？ | 用本次运行的真实数字：{墙钟}、{credits} |
| 规范是 AWS 预置的吗？ | AI-DLC 只给空的结构，规范由企业自己填；demo 里的是示例 |
| 越界改动会被拦住吗？ | 这个团队应用是事后检查、标红；运行时拦截靠 Kiro Crew 的审批和 hooks |

## 复用说明

| 要换的 | 换成什么 |
