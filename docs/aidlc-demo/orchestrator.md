# 编排器：「多 Agent 团队」app 怎么工作

第一版 demo 的编排器是 kirocrew-team，一个跑在 Kiro Crew 上的 app，由同事开发（私有仓库，代码不在这里）。demo 在它的 `demo/aidlc-im` 分支上加了接手已有项目所需的功能。这里只说明它怎么工作。

## 一句话

团队是一份 JSON 配置：有哪些角色、谁依赖谁、每个角色能改哪些目录、交什么产出。app 按依赖关系派活，每个角色是一个 Kiro Crew 的子 agent，在自己的 git worktree 里干活；app 负责合并、跑测试、按测试结果和评审意见把活打回给负责的角色。人只在关卡上拍板。

## 一次运行的流程

1. **建仓库**：把要接手的项目复制成运行仓库，叠加规范包（AI-DLC 官方专家定义 `aidlc/official/`、公司规范 `aidlc/knowledge/`、公司下发的检查 `tests/enterprise/`），提交为基线。
2. **派活**：依赖都合并了的角色开工。每个角色一条分支、一个 worktree，任务说明里写明它能改的目录、要先读的上游产出。没有依赖关系的角色同时干活。
3. **合并**：角色交活后，app 替它提交遗留的改动，记下它改了哪些文件；改了别人目录的记为越界；然后合进运行分支（`--no-ff`）。合并冲突打回给这个角色。
4. **测试**：每次有实现合进来，app 自己跑一遍全部检查（一个文件一个文件跑 `node --test`），不听 agent 自己说"改好了"。检查的文件名决定失败归谁修，失败的用例打回给负责的角色，最多修几轮由配置决定。
5. **评审**：所有角色都合进来、测试稳定以后，一个只读的评审 agent 看运行分支相对基线的全部改动。它说"要改"时写明打回给哪些角色，app 把意见原文发给它们修，修完重新测试、复审，最多 2 轮，之后交给人决定。
6. **看板**：每个角色的状态、测试墙（按功能、安全、合规、上架分组）、事件流、每个角色的产出和工具调用，都实时显示；运行结束后可以回看。

## 第一版的团队（`team-im.json`）

架构师 → 产品经理 ∥ 体验设计 ∥ 合规与安全 → 测试（等产品经理）∥ 后端 ∥ 网页前端 ∥ 安卓 ∥ 运维（等合规与安全，网页和安卓还等体验设计）→ 评审。10 个角色，默认模型 claude-sonnet-5.5，测试打回最多 3 轮，评审打回最多 2 轮。

每个角色的任务说明都要求先读 AI-DLC 官方的对应专家定义，再按公司规范干活。合规与安全把规范写成机器能判的检查，接手前应该是红的；测试写"不许改坏"的护栏，接手前应该是绿的。

## 设计上的几个取舍

- **不造引擎**：agent 用 Kiro Crew 原生的子 agent，会话、审批、审计、并发控制都用平台的。
- **测试说了算**：合不合格由 app 跑的检查决定，评审只看检查看不到的地方。
- **各改各的目录**：每个角色只能改分给它的目录，越界的改动会被记下来、交给人看。
- **出错有去处**：测试失败、评审要改、合并冲突，都按规则打回给负责的角色；轮数用完交给人。
